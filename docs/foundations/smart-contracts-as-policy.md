# 스마트컨트랙트와 정책 모델

## 문서 목적

스마트컨트랙트를 단순한 코드 배포가 아니라 상태 전이 규칙과 권한 정책을 고정하는 구조로 설명한다.

## 핵심 요약

- 스마트컨트랙트는 상태 전이 규칙을 공통 기준으로 고정하는 정책 레이어다.
- 중요한 것은 코드 그 자체보다 어떤 상태를 누가 어떻게 바꿀 수 있는가다.
- 이벤트 로그는 오프체인 서비스와 연결되는 핵심 인터페이스다.
- 실무 설계에서는 권한 모델, 업그레이드 정책, 감사 추적을 함께 봐야 한다.

## 실행 구조

```mermaid
flowchart LR
    A["사용자 또는 서비스"] --> B["트랜잭션 / 호출"]
    B --> C["실행 환경"]
    C --> D["컨트랙트 로직"]
    D --> E["상태 변경"]
    E --> F["이벤트 로그"]
    E --> G["권한 / 자산 / 정책 상태 변화"]
```

## 스마트컨트랙트의 본질

스마트컨트랙트는 `공개 검증 가능한 상태 머신`으로 이해하는 편이 좋다. 특정 주체가 임의로 규칙을 바꾸거나 결과를 조작하지 못하게 하려면, 상태 전이 규칙이 공통으로 재현 가능해야 한다.

실무에서는 아래 질문이 더 중요하다.

- 어떤 함수가 누구에게 열려 있는가
- 어떤 상태를 읽고 갱신하는가
- 어떤 이벤트를 남기고 누가 이를 소비하는가
- 실패 시 어디까지 롤백되는가
- 업그레이드와 긴급 정지는 어떤 통제 아래 있는가

## 권한 모델을 어떻게 볼 것인가

스마트컨트랙트는 권한 모델과 함께 설명해야 한다.

|모델|설명|
|---|---|
|Owner|단일 관리자 중심의 통제|
|RBAC|역할별 권한 분리|
|Multi-sig|여러 승인 주체의 합의 필요|

서비스 리스크가 높아질수록 권한을 세분화하고 감사 가능한 방식으로 남기는 것이 중요하다.

## 설계 시 자주 보는 쟁점

- 업그레이드 가능한가, 불변으로 둘 것인가
- 관리자 권한은 얼마나 강한가
- 이벤트 스키마를 어떻게 고정할 것인가
- 이벤트 로그만으로 충분한 추적이 가능한가

## 세미나 관점 메모

- 기본기 세션에서는 EVM 세부 구현보다 `정책을 어디에 둘 것인가` 질문으로 설명하는 편이 좋다.
- 이벤트 로그, 권한, 업그레이드, 비상정지 같은 항목은 이후 운영 세션으로 연결된다.
- 토큰 논의는 이 문서에서 깊게 확장하지 않고, 자산/정산/권리 구조 문서로 연결한다.
